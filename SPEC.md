# Termnest — SSH-клиент для Windows (спецификация)

> Рабочее название `termnest` — можно поменять в любой момент.
> Документ для Claude Code: реализуй **строго по этапам** (раздел 9), после каждого этапа приложение должно собираться и работать.
> **Перед началом любой работы — раздел 10 (Git и GitHub).**

---

## 1. Цель и рамки

Личный SSH-клиент под Windows 10/11 с нужным мне набором функций, без лишнего.

- Только Windows (x64). Кроссплатформенность не нужна, но и намеренно ломать её не надо.
- **Без Electron** — приоритет на низкое потребление памяти.
- **Аутентификация только по ключам.** Пароли от серверов не сохраняются никогда. Единственное место, где вводится пароль, — одноразовая установка ключа на сервер (раздел 5.3), пароль живёт только в памяти на время операции.
- Один пользователь, локальное хранение, без синхронизации и облака.

## 3. Архитектура

### 3.1 Главный принцип
**Источник истины — Rust-ядро. Окна и вкладки — только представления.**

- Каждое SSH-подключение — объект `Session` с уникальным `SessionId`, живёт в `SessionManager` в бэкенде, независимо от UI.
- Панель терминала во фронтенде лишь **подписывается** на вывод сессии по её id и шлёт ввод.
- Состояние раскладки (окна → вкладки → дерево сплитов → панели → `SessionId`) тоже хранится в Rust (`LayoutManager`), окна получают его через события.

Следствия, которые должны работать:
- перенос вкладки в другое окно **без переподключения**;
- закрытие окна не обязано рвать сессии (поведение настраивается);
- SFTP открывается **отдельным каналом в том же SSH-соединении**, без повторного входа.

### 3.2 IPC
- Вывод сессии → фронт: `tauri::ipc::Channel<Vec<u8>>` на каждую подписку (бинарно, без JSON для данных терминала).
- Ввод: команда `session_write(id, bytes)`.
- Размер: `session_resize(id, cols, rows)`.
- Состояние сессии (`connecting | connected | reconnecting | disconnected | error`) — событие `session://state`.
- Изменения раскладки — событие `layout://changed` всем окнам.

### 3.3 Структура проекта (ориентир)
```
src-tauri/src/
  main.rs
  commands/          # tauri-команды, тонкий слой
  session/           # SessionManager, Connection, реконнект, keepalive
  hostkeys/          # known_hosts, отпечатки
  keys/              # список/генерация/импорт/установка ключей
  sftp/              # операции и очередь передач
  layout/            # окна, вкладки, дерево сплитов, сохранение/восстановление
  storage/           # hosts.toml, snippets.toml, settings.toml, пути
  error.rs
src/
  lib/terminal/      # обёртка над xterm.js
  lib/layout/        # вкладки, сплиты
  components/        # менеджер серверов, сниппеты, SFTP, диалоги
  stores/
```

## 4. Хранение данных

Папка: `%APPDATA%\termnest\`

| Файл | Что внутри |
|---|---|
| `hosts.toml` | серверы и группы: имя, host, port, user, путь к ключу, группа, заметка |
| `snippets.toml` | сниппеты |
| `settings.toml` | шрифт, тема, хоткеи, поведение при закрытии, автовосстановление |
| `layout.json` | последняя раскладка окон/вкладок/сплитов |
| `known_hosts` | собственный файл отпечатков (формат OpenSSH) |

- **Никаких паролей и passphrase на диске.** Хранится только *путь* к приватному ключу.
- Запись атомарная (временный файл → rename), чтобы не побить конфиг при падении.
- В логах — никаких секретов и содержимого ключей.

## 5. Функции

### 5.1 Подключение и терминал
- Подключение по приватному ключу (ed25519, RSA, ECDSA).
- Ключ с passphrase: запросить в диалоге, держать в памяти до выхода (опция «не запоминать»).
- **Проверка ключа хоста:**
  - неизвестный хост → диалог с SHA256-отпечатком, «Доверять» / «Отмена»;
  - отпечаток изменился → **жёсткая блокировка** с предупреждением, продолжить можно только явным удалением старой записи.
- Keepalive (настраиваемый интервал).
- xterm.js: корректный ресайз, 256 цветов/truecolor, поиск (Ctrl+Shift+F), кликабельные ссылки.
- Копировать Ctrl+Shift+C, вставить Ctrl+Shift+V и правый клик; опция «копировать при выделении».
- Предупреждение при вставке многострочного текста.

### 5.2 Менеджер серверов
- Боковая панель: группы (сворачиваемые), поиск/фильтр, двойной клик — подключиться.
- Создать / редактировать / дублировать / удалить сервер.
- Быстрое подключение без сохранения: строка `user@host:port`.
- Импорт из `~/.ssh/config` (Host, HostName, User, Port, IdentityFile) — по кнопке.

### 5.3 Ключи: выбрать и закинуть на сервер
Отдельный раздел «Ключи».

**Список ключей**
- Показывает ключи из `%USERPROFILE%\.ssh\` и добавленные вручную: имя, тип, SHA256-отпечаток, есть ли passphrase.
- «Скопировать публичный ключ» в буфер.

**Сгенерировать ключ**
- Тип: ed25519 (по умолчанию) или RSA 4096; комментарий; опциональная passphrase.
- Сохраняет пару в `.ssh` в формате OpenSSH. Права на приватный файл — только текущему пользователю (ACL).
- Не перезаписывает существующие файлы без явного подтверждения.

**Установить ключ на сервер** (аналог `ssh-copy-id`)
1. Выбрать сервер из списка или ввести `user@host:port`.
2. Выбрать ключ из списка или сгенерировать новый прямо в диалоге.
3. Ввести пароль от сервера (одноразово, только в памяти).
4. Подключиться по паролю (с той же проверкой ключа хоста) и выполнить установку:
   - создать `~/.ssh` (700) и `authorized_keys` (600), если их нет;
   - добавить публичный ключ, **только если его там ещё нет** (без дублей);
   - **публичный ключ передавать через stdin exec-канала** (или SFTP), не подставляя в строку shell-команды.
5. **Проверка:** новое подключение уже по ключу. Показать результат: работает / не работает с причиной.
6. При успехе — предложить привязать этот ключ к серверу в `hosts.toml` (если сервер ещё не сохранён — предложить сохранить).
7. Пароль затирается из памяти сразу после операции.

**Опционально: отключить вход по паролю** (кнопка после успешной установки, не по умолчанию)
- Доступно только если вход по ключу **уже проверен** и пользователь root (или есть sudo без пароля), иначе показать инструкцию вручную.
- Порядок строго такой:
  1. не закрывать текущее соединение;
  2. создать drop-in `/etc/ssh/sshd_config.d/00-termnest-keys-only.conf` с `PasswordAuthentication no` (имя с `00-`, чтобы шёл раньше `50-cloud-init.conf` — в sshd побеждает первое значение);
  3. `sshd -t` — при ошибке удалить файл и прервать;
  4. `systemctl reload ssh` или `sshd` (что есть);
  5. **новым** соединением проверить вход по ключу;
  6. если проверка не прошла — удалить drop-in, reload, сообщить об ошибке.
- Перед запуском — экран подтверждения с объяснением, что произойдёт.

### 5.4 Вкладки и сплиты
- Вкладки: открыть, закрыть, переименовать, перетащить для смены порядка, цвет-метка.
- Сплиты: вертикальный/горизонтальный, произвольная вложенность (дерево), изменение размеров перетаскиванием, переход фокуса хоткеями.
- В заголовке панели — имя сервера и индикатор состояния.
- Дублировать сессию (новое подключение к тому же серверу) — Ctrl+Shift+D.

### 5.5 Несколько окон
- Новое окно (Ctrl+Shift+N).
- Вкладку можно: вытащить за пределы окна → новое окно; перетащить в другое окно; через контекстное меню «Переместить в окно…» / «В новое окно».
- Перенос **не переподключает** сессию.
- Поведение при закрытии окна с активными сессиями — настройка: спросить / закрыть сессии.

### 5.6 Сохранение сессий (восстановление раскладки)
- Раскладка сохраняется в `layout.json` при изменениях (с debounce) и при выходе: окна (позиция, размер), вкладки, дерево сплитов, к какому серверу каждая панель.
- При запуске: восстановить всё и переподключиться (настройка: автоматически / спросить / нет).
- Процессы на сервере при этом **не сохраняются** — это ожидаемо (tmux вне рамок).
- **Авто-реконнект** при обрыве: экспоненциальная задержка (1, 2, 4… до 30 с), оверлей «Переподключение…» в панели с кнопками «Сейчас» / «Отмена». Если пользователь сам закрыл сессию — не переподключать.
- Панели, к которым подключиться не удалось, остаются на месте с ошибкой и кнопкой «Повторить».

### 5.7 Сниппеты
- Поля: название, команда, теги, флаг «нажимать Enter».
- Переменные `{{имя}}` — при отправке спросить значения.
- Палитра (Ctrl+Shift+P): поиск по названию/тегам, Enter — отправить.
- Куда отправить: текущая панель / выбранные / все панели вкладки / все сессии.
- Режим **broadcast**: ввод с клавиатуры дублируется в выбранные панели, хорошо видимый индикатор, что режим включён.

### 5.8 SFTP
- Боковая панель к активной сессии (тот же SSH-коннект, отдельный канал).
- Навигация, хлебные крошки, «перейти в текущую папку терминала» (по возможности).
- Загрузка: кнопка и drag & drop из Проводника. Скачивание: в выбранную папку.
- Создать папку, переименовать, удалить (с подтверждением), права (chmod) — просмотр и изменение.
- Очередь передач с прогрессом, скоростью, отменой; несколько файлов и папки целиком.
- Конфликт имён: спросить — заменить / пропустить / переименовать.

### 5.9 Настройки и внешний вид
- Тёмная тема по умолчанию + несколько тем на выбор, шрифт и размер, межстрочный интервал, курсор.
- Таблица хоткеев с возможностью переназначения.

## 7. Нефункциональные требования
- Холостой ход с одним окном и одной сессией — минимально возможное потребление памяти; без фоновых таймеров во фронте сверх необходимого.
- 10+ одновременных сессий без подтормаживаний ввода.
- Рендер терминала — webgl-аддон, с фолбэком на canvas.
- Ошибки — понятные сообщения пользователю (нет доступа, неверный ключ, таймаут, хост недоступен), а не паника.
- Сборка: см. раздел 7.1.

### 7.1 Сборка: Docker и нативно

Docker здесь — **воспроизводимая среда сборки и тестов**, а не среда запуска. Приложение — десктопное GUI под Windows, оно всегда запускается обычным `.exe` вне Docker.

**Основной путь — сборка в Docker (Linux-контейнер, кросс-компиляция под Windows):**
- `docker/Dockerfile`: Rust (stable, версия зафиксирована), target `x86_64-pc-windows-msvc`, `cargo-xwin`, `llvm`, `lld`, `clang`, `nsis`, Node.js LTS (версия зафиксирована).
- `docker-compose.yml` с сервисами:
  - `build` — `npm ci` + `npm run tauri build -- --runner cargo-xwin --target x86_64-pc-windows-msvc`;
  - `test` — `cargo test` для ядра, `cargo clippy -- -D warnings`, проверка фронта (`npm run check`, линтер).
- Кэш cargo registry, `target/` и `node_modules` — в именованных volume, чтобы повторные сборки были быстрыми.
- Результат копируется в папку `release/` в корне проекта: NSIS-инсталлятор (`*-setup.exe`) и сам `termnest.exe` (portable).
- Скрипт-обёртка `scripts/build.ps1` для запуска из PowerShell одной командой: `./scripts/build.ps1` (сборка) и `./scripts/build.ps1 -Test` (тесты).
- Ограничение: из Linux-контейнера собирается только **NSIS**-инсталлятор; `.msi` (WiX) требует Windows — это нормально, NSIS достаточно.

**Альтернативный путь — нативная сборка на Windows (без Docker):**
- Требования описать в `README.md`: Rust (MSVC toolchain), Visual Studio Build Tools (C++), Node.js LTS, WebView2 (есть в Windows 11).
- `npm run tauri build` — даёт и NSIS, и `.msi`.
- `npm run tauri dev` — режим разработки с горячей перезагрузкой. **Запуск и отладка GUI — только нативно**, внутри Docker приложение не запускается.

**Требования:**
- Обе сборки должны давать рабочий результат из одного и того же кода, без правок под конкретный путь.
- Сборка в Docker не должна требовать ничего, кроме Docker Desktop.
- `release/` — в `.gitignore`.
- Бинарники в git не коммитить; при желании позже — GitHub Actions + Releases (вне рамок сейчас).

## 9. Этапы

Каждый этап — рабочая сборка. Не переходить к следующему, пока критерии не выполнены.

**Этап 1. Скелет**
Tauri 2 + Svelte + xterm.js; одно окно, одна панель; подключение по ключу к `user@host:port` из поля ввода; ресайз; копипаст. Docker-сборка и тесты (раздел 7.1) настраиваются **на этом же этапе**, до остальных функций.
Готово, когда: `./scripts/build.ps1` собирает в Docker `release/termnest.exe` и инсталлятор; этот `.exe` запускается на Windows вне Docker; подключаюсь к своему серверу, работают `htop` и `nano`, окно ресайзится без артефактов.

**Этап 2. Менеджер серверов + known_hosts**
`hosts.toml`, CRUD, группы, поиск, быстрое подключение, импорт из `~/.ssh/config`; проверка ключа хоста; passphrase.
Готово, когда: Сервер сохраняется и открывается двойным кликом; новый хост спрашивает отпечаток; подменённый — блокируется.

**Этап 3. Ключи**
Список, генерация, копирование публичного ключа, мастер «Установить ключ на сервер» с проверкой; опциональное отключение входа по паролю.
Готово, когда: Свежий сервер с паролем → через мастер ставлю ключ → подключаюсь без пароля; повторная установка не создаёт дубль в `authorized_keys`.

**Этап 4. Вкладки и сплиты**
Готово, когда: 3 вкладки, в одной — 4 панели в сплитах к разным серверам, всё ресайзится и переключается хоткеями.

**Этап 5. Несколько окон**
Готово, когда: Вытаскиваю вкладку в новое окно и возвращаю обратно — сессия не переподключается, вывод не теряется.

**Этап 6. Сохранение раскладки и реконнект**
Готово, когда: Закрываю приложение с 2 окнами и сплитами → открываю → всё на своих местах и переподключено; рву сеть → панель переподключается сама.

**Этап 7. Сниппеты и broadcast**
Готово, когда: Сниппет с переменной отправляется во все панели вкладки; broadcast-ввод идёт в выбранные панели, индикатор виден.

**Этап 8. SFTP**
Готово, когда: Перетаскиваю папку из Проводника на сервер с прогрессом, скачиваю файл, переименовываю, удаляю с подтверждением.

**Этап 9. Полировка**
Темы, настройки, переназначение хоткеев, иконка, инсталлятор.
Готово, когда: и Docker-сборка, и нативная `npm run tauri build` дают рабочий инсталлятор; приложение ставится и запускается на чистой Windows 11.

## 10. Git и GitHub

**Перед тем как писать код:**
1. Проверить, что установлены `git` и GitHub CLI (`gh`) и выполнен вход (`gh auth status`). Если нет — остановиться и попросить меня залогиниться (`gh auth login`), не обходить это.
2. `git init`, ветка по умолчанию `main`.
3. Добавить `.gitignore` для Tauri/Rust/Node (`target/`, `node_modules/`, `dist/`, `release/`, `src-tauri/gen/`, файлы IDE, `.env`).
4. Первый коммит: `SPEC.md`, `.gitignore`, короткий `README.md`.
5. Создать **приватный** репозиторий и запушить: `gh repo create termnest --private --source=. --remote=origin --push`.

**В процессе работы:**
- Коммит после **каждого логически завершённого шага** внутри этапа (не один коммит на весь этап), и обязательно коммит в конце этапа.
- Перед коммитом проект должен собираться и проходить тесты (`docker compose run --rm test` или `cargo check` + сборка фронта нативно); нерабочий код не коммитить.
- Сообщения коммитов — в формате Conventional Commits, на английском: `feat(keys): add key deploy wizard`, `fix(session): handle reconnect on timeout`, `chore: ...`, `refactor: ...`, `test: ...`, `docs: ...`.
- После каждого коммита — `git push`.
- В конце этапа — тег: `git tag stage-1` (`stage-2` и т.д.) и `git push --tags`.
- Никогда не коммитить ключи, пароли, `known_hosts`, `hosts.toml` с реальными серверами и прочие личные данные. Перед коммитом проверять `git status` / `git diff --staged`.
- Без `git push --force` в `main`.

- **Никаких эмодзи** — ни в коде, ни в комментариях, ни в UI-текстах, ни в логах, ни в сообщениях коммитов, ни в README и документации. Для статусов в интерфейсе — иконки (SVG) или текст.
- Работай по одному этапу; в конце этапа — краткий список того, что сделано и как проверить.
- Логику ядра (сессии, layout, hosts/known_hosts, установка ключа) покрывай unit-тестами в Rust, где это разумно.
- Секреты (пароль, passphrase) — в типах, затирающих память при drop (`zeroize`/`secrecy`); не логировать, не сериализовать.
- Перед добавлением зависимости — коротко объясни, зачем она.
- Если что-то в спецификации неоднозначно или противоречит ограничениям библиотек — спроси, а не угадывай.
